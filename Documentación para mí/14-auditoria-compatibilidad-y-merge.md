### Cómo completar la evidencia con acceso autorizado

1. Ejecutar [la consulta de inventario](../tooling/versioning/audit-historical-releases.sql) en OPS con un rol de lectura y exportar la única columna `snapshot` como objeto JSON. La transacción es de solo lectura, tiene un tiempo límite y termina en rollback. No consulta solicitudes de despliegue. El corte es la hora del commit de seguridad. El alcance incluye releases anteriores de ambos productos en los tres entornos y sus antecesoras, incluso si una referencia inconsistente cae fuera de ese conjunto. Se excluyen campos libres innecesarios.
2. Confirmar que los permisos de lectura permiten ver todas las filas de la auditoría y sus vistas. Si RLS oculta filas, dejar el caso pendiente hasta tener evidencia completa. Se necesitan `version_releases`, `version_products`, `version_environments`, `version_releases_labeled`, `version_promotions`, `version_release_artifacts` y `version_release_artifacts_labeled`. Una ausencia observada con permisos incompletos no prueba que se haya borrado el ZIP. [Tablas de releases y promoción](../apps/referidos-ops/supabase/migrations/20260221_000014_versioning_system.sql#L268) · [Vista actual de releases](../apps/referidos-ops/supabase/migrations/20260313_000029_versioning_release_metadata_builds.sql#L327)
3. Para cada ID seleccionado por linaje, guardar los bytes de una lectura autorizada. Para Storage, verificar el objeto en el bucket y ruta exactos. La lista del catálogo es evidencia parcial. Para Actions, se necesitan los campos del registro `id`, `name`, `workflow_run.id` y `expired` del repositorio esperado, además de la descarga por ese ID. Conservar el ZIP o contenedor como `<artifact-id>.zip` fuera de los archivos versionados. Guardar únicamente la evidencia mínima en JSON. Evitar tokens, URLs firmadas y cuerpos de error.
4. Pasar el export a [la herramienta local](../tooling/versioning/audit-historical-releases.mjs). Usa las comprobaciones de metadatos del workflow, los helpers puros del callback y el verificador de ZIP de producción. Reconstruye el linaje en memoria a partir del export. Su único cambio de archivos es la extracción del ZIP bajo un directorio temporal propio, que retira al terminar. El informe JSON incluye una fila por release, IDs de las promociones, artefacto dueño, huella, tamaño y compatibilidad con los tres formatos de callback. El proceso nunca llama a OPS ni a Actions.

```powershell
node tooling/versioning/audit-historical-releases.mjs --snapshot C:/ruta/export-ops.json --repository sebasApps-lab/referidos-app
node tooling/versioning/audit-historical-releases.mjs --snapshot C:/ruta/export-ops.json --repository sebasApps-lab/referidos-app --evidence C:/ruta/evidencia.json --archives C:/ruta/zips
```

En el archivo de evidencia, `storage` y `github` son objetos indexados por UUID de artefacto. Cada observación de Storage incluye `bucket`, `path` y `result`. En GitHub incluye `repository`, `result` y, si la consulta tuvo acceso al registro, `record`. Usar `downloaded` solo al descargar el objeto exacto, con `checked_at` en ISO 8601, `file_sha256` y `file_size_bytes` de los bytes recibidos. Para Actions esos campos describen el archivo descargado antes de extraerlo. La utilidad los contrasta con la copia local y verifica por separado la huella registrada del ZIP interior. Usar `listed` para catálogo, `missing` solo cuando la ausencia esté verificada y `unauthorized` si faltan permisos. El instante describe la observación del operador, que el proceso offline no puede renovar por su cuenta.

Para registros sin bucket propio, usar `--default-bucket` si la configuración autorizada de GitHub elige un fallback distinto de `versioning-artifacts`. El código de salida `0` requiere evidencia offline completa para todas las filas exportadas. El código `2` indica matriz vacía, bloqueos o evidencia incompleta. El código `1` indica que el import o la invocación falló. `verified_offline_evidence` cubre procedencia y archivo con la evidencia entregada. Para Desarrollo indica origen de la build. La autorización nueva, la configuración del tenant, la lectura de `app-config.js` por la aplicación y el comportamiento de un workflow alojado se evalúan en otro paso.

## 5. Recomendación por grupo y siguiente revisión

- **Documentación y herramientas de auditoría.** Técnicamente listas para revisión separada. Los resultados simulados comprueban el contrato local.
- **Android.** Autenticación por correo y registro de dispositivo tienen cobertura simulada favorable. La promoción requiere resolver la escritura de rol e invitación, reproducir el APK y probar una instalación limpia y otra actualizada. Incluir login desde cierre forzado, refresh y expiración, revocación y registro idempotente por dispositivo, MFA y regreso desde OAuth, salto al rol correcto, navegación hacia atrás y QR con y sin permisos.
- **PWA.** El build y los casos simulados de login y logout son favorables. El grupo requiere corregir la entrada al registro, la recuperación y el manejo de sesión pendiente. Faltan OAuth y MFA con una cuenta de prueba, PWA instalada con regreso fuera del navegador, restauración tras recarga, cierre con scopes y pérdida de red. Prelaunch y la PWA histórica tienen resultados de build y lint favorables.
- **OPS y telemetría.** Bloquear aprobación de este grupo hasta resolver acceso, purga y confirmaciones descritos arriba. Probar dos administradores, scopes de tenant, AAL1/AAL2, conciliación manual, rechazo y aprobación, pérdida de resultado del pipeline y migraciones con resultados tardíos.
- **Versionado.** La integridad simulada pasa. Antes de autorizar la siguiente etapa, completar la matriz con ambos productos y cada entorno, al menos una cadena promovida, una release antigua con evidencia insuficiente y un callback legado. Conservar la política de no reutilizar solicitudes existentes y documentar la configuración runtime aprobada del entorno.
